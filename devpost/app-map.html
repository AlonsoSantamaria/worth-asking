Worth Asking · reference map

One answer, a recalculated decision.

The app compares two offers, asks about influential missing information, and tests whether remaining uncertainty can reverse the preferred offer. Calculations run in the browser; there is no runtime AI service, database, or persistent session.

Source snapshot: public 33c4536, corresponding to tested application candidate 549950d. This is a reference route and brief static recap, not a record of a completed learner-led tour. It can drift if the source changes.

Follow the real flow

1. Enter office evidence

QuestionCard.submit → applyEvidence → sessionReducer

Check the answer against the domain and supplied range. A blank answer stays unknown; invalid answers do not replace the valid result.

↓ new decision input
2a. Compare and test every allowed combination

evaluate → compare → attainableBounds → recommend

Exact weighted utility and full independent-box extrema determine STOP / CONTINUE. This branch never relies on scenario sampling.

2b. Prioritize the next question

prioritizeQuestions → constructScenarios

Complete endpoint thought experiments estimate the reduction in modeled decision loss. Their weights are assumptions, not empirical probabilities.

↓ one evaluation result

3. Show the current result

App → OfferCard + UpdateSummary + readiness/verdict

The cards read current evidence and computed scores. The summary compares one previous valid result with the new one. A stable winner yields DECIDE NOW; unsettled ranges retain KEEP INVESTIGATING; a modeled tie stays inconclusive.

A three-stop source route

  1. QuestionCard.tsx, submit; then evidence.ts, applyEvidence. Office answers 5 and 1 become validated evidence rather than display-only text. sessionReducer reevaluates and retains one previous valid result.
  2. evaluate.ts, evaluate. Follow compare, attainableBounds, recommend, and prioritizeQuestions. Bounds and question ranking answer different questions and remain separate.
  3. App.tsx, the verdict using result.policy.action. OfferCard renders the computed comparison; UpdateSummary shows the reversal. No production branch stores the golden outcome.

To change this, start here

  • Offer information or score presentation: src/components/OfferCard.tsx and src/styles.css.
  • Evidence validation: src/engine/evidence.ts, validation.ts, and their unit tests.
  • Question ordering: src/engine/questions.ts; stopping: bounds.ts and policy.ts. Changes to these semantics require product/architecture review.
  • Regression coverage: tests/e2e/decision.spec.ts, offer-cards.spec.ts, and src/engine/__tests__.

Pointers are explanatory. WA-05 authorizes no product edits.

A practice to reuse

Turn a requirement into observable assertions, then trace those assertions to the implementation. Here the original 63/53 result is insufficient proof: the evidence transaction must calculate both 43/65 for 5/1 and 83/33 for 0/5. The browser tests assert the scores, gap bounds, verdict, and updated profile. The combined-uncertainty unit test separately prevents a sampled or one-at-a-time analysis from claiming a false STOP.

This separates a persuasive demo from evidence of the behavior. Reuse the same pattern on another project: state the expected transition and one counterexample, find the responsible function, and test both before claiming it works.
